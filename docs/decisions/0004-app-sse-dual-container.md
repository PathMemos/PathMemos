# 0004: app 与 sse 双容器共享同一镜像 + Redis

- 状态：已接受
- 日期：2026-07
- 取代：无

## 背景

AI 对话是长连接 SSE，若与普通 REST 同进程，慢连接会占满连接数并拖累其它接口；但另写一套 SSE 代码维护成本高。

## 决策

**我决定**：同一镜像启动 HTTP(`:8080`) 与 SSE(`:8081`) 两个监听，分别部署为 `app`、`sse` 容器，由 nginx 按路径分流（`/ai/chat` → sse，其余 → app）。两容器跨进程只共享 Redis（session/锁/配额/缓存），不依赖共享内存。

## 备选方案

- 单容器：否决——SSE 挤占 REST 连接与内存。
- 独立 SSE 代码库：否决——双份业务逻辑维护成本。

## 后果

### 正面

- 故障隔离，SSE 可与 REST 独立重启/扩容。

### 负面 / 代价

- 两个容器都会启动后台任务——**有意取舍**：同镜像对称启动、无角色配置（不区分「谁跑后台」），任务并发互斥由 PostgreSQL advisory lock 承担（见 [ADR-0005](0005-distributed-locks-postgresql.md)），双容器竞争落败方直接 skip 空转、成本可忽略；单角色化省不了真实成本反增配置面；任务自身幂等保证重复触发不产生重复数据。
- 不能依赖进程内状态，缓存/限流语义需跨进程一致。
