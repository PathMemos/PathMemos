# 0016 open_id 首注渠道语义与跨端删号重注册绕过权益墓碑已接受

日期：2026-09-29｜状态：已接受

## 背景

`users.open_id` 为「首次注册渠道标识」：小程序渠道注册存**微信小程序 openid**，多端 App 渠道注册存**多端侧 openid**（`auth/handler.go` LoginApp 以 `DonutCode2VerifyInfo` 返回的 OpenID 构建 WechatSession，2026-09-29 终版登录链路）。跨端身份归一依赖 `unionid`：`findOrCreateUser` 先按 unionid 查存量用户，命中即复用同一行；因此双端并存用户的两个 openid 归一到同一条用户记录。

防「注销循环薅权益」的墓碑（000008：`user_vip_claims.open_id`、`user_invites.user_open_id`）以 open_id 为防重主体。其绕过前提：**仅当「先经 A 渠道注册 → 删号 → 从 B 渠道重注册」**时，新行 open_id 为另一体系标识，墓碑不命中，7 天试用/免费 VIP/被邀请 +3 可再次领取。同端删号重注册 openid 不变、墓碑有效；双端并存用户不受影响。

## 决策

**接受该风险，不改墓碑键**。理由：

- 绕过需用户主动删号（自删全部数据）并切换注册渠道，属对抗性滥用而非偶然路径；普通双端用户由 unionid 归一保护。
- 墓碑键改 unionid 需要历史数据迁移，且小程序渠道 unionid 依赖开放平台绑定关系（存在缺失场景），改动收益/风险比不划算。
- 与 INVARIANTS §9 已接受的邀请侧 +7 天风险同一量级；000008 的主目标（同端循环薅取）仍然被有效拦截。

## 后果

- 触发条件：出现真实跨端删号重注册薅取案例时，墓碑键改为 unionid（配合存量数据一次性回填）。
- 文档口径：02a §4.1 与 04 §3.1 统一为「首次注册渠道标识」；07 F13 涉及表描述同步。
