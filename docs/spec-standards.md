# Spec 模式规范（规格先行开发约定）

> 先写规格、再写代码、代码必须回写规格。
> 本规范参考 `zhima / xiaozhi` 两项目共用的统一规范：§二~§九 为通用模板正文（跨项目语义一致），§一 为本项目文件映射。
> 本文件是 PathMemos-SaaS 的 spec 母法；仓库根目录 `AGENTS.md` 是第一入口。

## 一、项目文件映射（PathMemos-SaaS）

| 层 | 文件 | 说明 |
|---|---|---|
| L1 PRD/总览 | `docs/spec/01-product-overview.md` | 业务目标 / 定位 / 功能范围 / 验收与测试覆盖 |
| L2 领域分册 | `docs/spec/02a-auth-account.md`、`02b-diary.md`、`02c-autorecord.md`、`02d-family-invite.md`、`02e-vip-payment.md`、`02f-ai-chat.md`、`02g-file-push.md`、`02h-mcp-open.md` | 每分册自足（背景/决策/流程/数据/契约/计划） |
| L3 接口契约 | `docs/spec/03-api.md` | 认证与请求头/统一响应/错误码词汇表/分页/限流/幂等 + 全量端点登记 |
| L4 数据库 Schema | `docs/spec/04-database.md` | ER/字段级表定义/数据字典（枚举、状态机）/ 迁移变更记录 |
| L5 开发计划与部署契约 | `docs/spec/05-development-plan.md` | 协作节奏/外部依赖/`deploy/deploy.sh` 契约/本地门禁 |
| L6 前端/交互 | `docs/spec/06-miniapp-pages.md` | 小程序页面清单（路由/优先级）/关键交互/全局规则（弹窗/表单/反馈/四态） |
| L7 验收流程 | `docs/spec/07-acceptance-flows.md` | 人工验收清单（场景/期望/异常核对）+ 覆盖登记表（需求编号 → 场景 / 不需场景的理由） |
| L8 能力索引 | `docs/CAPABILITIES.md` | 全平台能力实时清单（按域分组），新增/变更能力时同步 |
| L9 决策记录 | `docs/decisions/` | ADR：只记「为什么这么做」，索引双向同步 |

判断规则：

- **改现有能力** → 回写对应层文件 + 更新 `CAPABILITIES.md`。
- **新增大模块** → 新建 L2 分册（套 §四 模板）+ 能力索引加一节。
- **bug 修复 / 纯重构** → commit message 写 `spec:nochange` 豁免，不改 spec。
- **文档移动/改名/删除** → 同一 commit 内更新全部引用。
- **一次性运维任务**（如服务器迁移、数据回捞）**不占 spec 层**，执行计划单独维护，不入库 `docs/`。

## 二、统一制品分层（九层模板）

每一层是一类制品，回答固定的问题、包含固定的小节。跨项目对齐靠层号，不靠文件名。

| 层 | 制品 | 必须回答 / 必须包含 |
|---|---|---|
| L1 PRD/总览 | 产品定位与需求基线 | 为什么做、给谁用、功能范围；业务目标 + 验收标准（AC）或模块卡片；非功能需求（性能/安全/兼容/可维护）；验收与测试覆盖 |
| L2 平台与领域分册 | 领域需求、引擎/子平台规格、落地示例 | 复用/新增/删除清单；每个分册自足（背景/决策/流程/数据/契约/计划） |
| L3 接口契约 | 全量 API 契约 | 必含小节：认证与请求头、统一响应结构、错误码词汇表（注明词汇规范源：spec 正文 + errors 包常量）、分页、状态码映射、超时与限流、数据归属校验约定、幂等约定；按域分组全登记 + 通用契约模板 |
| L4 数据库 Schema | ER、表定义、字典 | ER 概览；字段级表定义；数据归属说明（user_id 归属 + 无归属表的豁免清单）；数据字典（枚举/状态机/软删除策略）；迁移变更流程 |
| L5 开发计划与部署契约 | 迭代节奏与运维契约 | 开发约定（协作模式/评审节点）、外部依赖、`deploy.sh` 部署契约（执行顺序/失败处理分类/密钥注入边界/备份恢复/质量门禁）、本地门禁与工具 |
| L6 原型/交互 | 页面清单与交互规范 | 页面清单（路由/优先级）、关键页面交互、全局交互规则（弹窗/表单/反馈/四态）、响应式规则 |
| L7 验收流程 | 人工验收清单 + 覆盖登记 | 人工验收场景（前置/步骤/期望/异常核对）+ 覆盖登记表（需求编号/链路 → 已有场景 / 不需场景 / 理由）；自动化门禁仅后端 Go 测试 |
| L8 能力索引 | 系统功能实时清单 | 全平台能力条目（按域分组），新增/变更能力时同步（spec-check 监控） |
| L9 决策记录 | ADR | 只记「为什么这么做」，索引双向同步 |

## 三、需求表达格式（二选一，验收标准必须可测试）

- **用户故事 + 验收标准（AC）**：推荐用于面向用户的产品功能，编号稳定（如 `D-1`、`P-3`）。
- **模块卡片**：概述/角色/页面/状态机/数据模型/接口；用于业务还原型模块或引擎分册。
- 两种格式的需求单元都必须有稳定编号或名称，并被 L7 覆盖登记表引用；验收标准必须可人工核对（可观察的期望结果），后端行为类标准还需能被 Go 单测断言。

## 四、领域分册模板（新建大模块时套用）

```
## 1. 背景与目标
## 2. 领域级架构决策
## 3. 核心流程（用户故事 + 时序）
## 4. 数据模型
## 5. API 契约
## 6. 关键实现约束
## 7. 前端接入
## 8. 运维与任务
```

> 以上为**现存分册的实际结构**（02a~02h 一致）；新建分册沿用此结构，不再使用旧的「开发计划/实施顺序」九节模板。

## 五、DoD（完成定义）

> **验收策略**：自动化测试仅保留**后端 Go 测试**（`make test`）作为门禁；小程序端到端与 Worker 行为以**人工验收**为准（L7 场景）。存量前端 Jest（套件/用例数以 `frontend/miniapp/test/` 实际为准，当前 9 套件/49 用例）与 Worker vitest（38+21）保留为资产但**不作为验收门禁**，不要求随新功能新增用例。

1. 代码实现 spec 能力，通过门禁（见 §九）在本机验证（页面交互由用户确认）。
2. 规格已同步：新增写入/变更更新对应层文件（§一 映射）。
3. 后端核心业务逻辑、关键状态机、关键数据访问**必须有 Go 单测**；DTO、薄封装、纯配置等按实际情况决定，不为覆盖率而覆盖。前端/Worker 无自动化测试要求。
4. API 变更同步 L3 契约文档；migration 配对 `.down.sql`；改 SQL 后跑 `make sqlc-generate` + `make check-sqlc-sync`。
5. 新建公共抽象前查复用情况 + ADR，并同步登记。
6. 核心业务链路同步登记/更新 L7 人工验收场景（纯局部改动豁免）。
7. 能力索引（L8）同步更新。

## 六、数据模型变更流程

1. **分配迁移号**：取 `backend/migrations/` 当前最大 +1，命名 `NNN_<slug>.up.sql` / `.down.sql`。
2. **down 可逆性**：不可逆操作在文件头声明 `-- 不可逆：<原因>`。
3. **同步 schema 文档**：同次提交回写 L4 文档的变更记录 + 对应小节字段定义。
4. **机械校验**：`spec-check.sh` 比对 migrations 编号与 L4 文档登记。

> 并行撞号规则：同号不同名允许（slug 全局唯一），改同一张表需 rebase 确认顺序。

## 七、一致性红线

- **新增能力**：先（或同时）写 spec，再写代码；禁止「只写代码不改 spec」。
- **行为变更**：改接口/状态机/错误码/权限必须同步 spec。
- **删除能力**：代码删除时同步删除 spec 描述。
- **发现不一致**：停下来向用户报告，不擅自判定谁对谁错。
- **引用方式**：跨文档引用代码优先「文件 + 函数/符号」（如 `auth/handler.go` `Logout`）；确需行号时由 `spec-check.sh` 的「file:line 引用范围」提示兜底。纯行号漂移（符号/语义未变）不要求单独修订文档。

## 八、七节点工作流

| # | 节点 | AI 做什么 | 产物 |
|---|---|---|---|
| 1 | 对齐意图 | 读 AGENTS.md + 相关 docs + ADR，确认红线 | 无 |
| 2 | 明确需求 | 澄清为 WHAT/WHY，不碰 HOW | spec 需求章节 |
| 3 | 制定方案 | 映射为技术方案，记录理由回链需求 | spec 架构/API/数据章节 |
| 4 | 拆解任务 | 生成任务清单，标依赖与并行 `[P]` | 任务清单 |
| 5 | 实现 | 代码 + 测试 + migration，**同时回写 spec** | 代码 + spec |
| 6 | 校验 | `spec-check.sh` 硬约束 + 语义自查 | 校验报告 |
| 7 | 收敛 | 评估实现，记录遗留项 | 收敛记录 |

### 关键原则

1. **spec 聚焦 WHAT/WHY，plan 才谈 HOW**。
2. **spec 是「生成器」不是「备份文档」**：描述必须能被 AI 无歧义转成代码。
3. **验收标准可人工核对**（可观察期望结果），后端行为类标准能被 Go 单测断言。
4. **行为契约 vs 实现锚点**：阈值语义、幂等、数据归属、状态机等**行为契约**的变更必须先改/同步对应 spec；文档中的具体键名、TTL 数值、文件路径、函数参数等是「**当前实现参考**」，代码演进时同步更新即可，不构成不可变约束。文档不区分「硬业务规则 / 推荐实现」的层级标签，以所在章节定性质：决策表（D-x）与不变量为约束，实现位置与键值清单为参考。

## 九、校验分工（`scripts/spec-check.sh` 门禁）

| 级别 | 项 | 内容 |
|---|---|---|
| 阻断 | 1 | spec 制品齐备（L1~L7 文件存在且非空，能力索引存在） |
| 阻断 | 2 | ADR 索引双向（文件 ↔ `decisions/README.md`） |
| 阻断 | 3 | migration 配对（up/down 成对） |
| 阻断 | 4 | migration 编号 ↔ L4 文档变更记录 |
| 阻断 | 5 | 安全红线（仓库内无密钥/口令；上传类型白名单） |
| 阻断 | 6 | spec 随代码变更：改了 `backend/`、`api-worker/`、`mcp-worker/` 而 spec/能力索引无同次变更，且 commit 无 `spec:nochange` → 失败 |
| 提示 | 7 | 路由 ↔ L3 契约覆盖（含外置豁免清单） |
| 提示 | 8 | 错误码词汇表 ↔ `backend/pkg/errors` 常量一致性（以 spec 词汇表为准） |
| 提示 | 9 | 新增后端实现文件带测试 |
| 提示 | 附 | down 不可逆标注、上传白名单、能力索引反向差异 |
| 提示 | 10 | spec 内 `file:line` 引用范围（文件存在且行号不超长） |
| 提示 | 11 | MCP 静态方法双源对账：`mcp-worker/src/lib.ts` 与 `backend/internal/mcp/server.go` 的 tools/prompts 名称与描述一致（`scripts/check_mcp_static_sync.py`） |
| 阻断 | 12 | `docs/` 无过程产物/评审残留（`R-xx`、`plans/`、`第三步整改`），只保留当前终态（对应 AGENTS §五） |

| 类型 | 手段 | 负责 |
|---|---|---|
| 硬约束（阻断） | `scripts/spec-check.sh` | 上表阻断级 |
| 温和提示 | `scripts/spec-check.sh` | 上表提示级 |
| 语言级门禁 | `make lint-go` / `make lint-frontend` / `make lint-worker` / `make check-sqlc-sync` | 本地全跑；CI 三个 job：backend（golangci-lint + `go test -race` + check-sqlc-sync + MCP 双源对账 + 连接预算脚本测试 + `spec-check.sh` + 静态模式审计 `audit-patterns.sh`（信息性））、frontend（`npm run lint`）、worker（typecheck） |
| 语义一致性 | AI analyze 节点 | spec↔代码是否对齐 |
| 业务链路 | L7 flow（手动/自动化冒烟） | 端到端验证 |

> 工具项口径与本文档如有出入：属「发现不一致」，按 §七 停下来报告，不擅自改。
